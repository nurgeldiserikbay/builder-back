# Development/test environment on Render

`render.yaml` in this repository describes a test copy of BuildPath on Render (workspace "dev-flow", region Frankfurt).
It is for development and trials only. Production stays on one server in Kazakhstan (`deploy/README.md`).

## What gets created

| Resource | Render type | Plan | Approx. cost / month |
|---|---|---|---|
| `buildpath-api` — API, migrations before each deploy, Telegram webhook | web (Docker, this repo) | Starter, 512 MB | $7 |
| `buildpath-app` — mobile web app and Telegram Mini App; `/api/*` is forwarded to the API | web (Docker, builder-front) | Starter, 512 MB | $7 |
| `buildpath-admin` — staff console | web (Docker, builder-admin) | Free, sleeps when idle | $0 |
| `buildpath-sites` — published customer sites | web (Docker, this repo, `node dist/sites.js`) | Free, sleeps when idle | $0 |
| `buildpath-db` — PostgreSQL 17 | Postgres | Basic-256mb, 1 GB disk | ≈ $6.30 |

Total ≈ **$20 per month** on the Hobby workspace plan ($0), plus traffic above 5 GB/month ($0.15/GB).
Prices are from render.com/pricing (November 2026); check before approving.

Free services sleep after 15 minutes without requests and take about a minute to wake up. For `buildpath-sites` this also
means booking reminders and lead cleanup run only while it is awake. Switch it to Starter (+$7) when that matters.

## Not included on this environment

- **Malware scanning (ClamAV).** It needs about 2 GB of memory (Standard, $25). Without it photo uploads are refused with a
  clear message; everything else works.
- **Design review worker and object storage** (staff tool) — not needed for the main flow.
- **Online payments.** `PAYMENTS_PROVIDER=mock` is ignored in production mode; balance top-ups are unavailable here.
- **Backups beyond Render's own daily snapshots.**

## Before creating

1. Merge the open pull requests into `main` in builder-back, builder-front and builder-admin: services deploy from `main`.
2. In Render, connect GitHub with access to the three repositories.

## Values asked for when the Blueprint is created

| Key | Value |
|---|---|
| `PUBLIC_APP_URL` | public address of `buildpath-app`, e.g. `https://buildpath-app.onrender.com` (Render may add a suffix if the name is taken) |
| `PUBLIC_API_URL` | public address of `buildpath-api` |
| `SITES_BASE_DOMAIN` | domain for published sites, e.g. `sites.example.kz`; leave a placeholder until a domain exists |
| `SITES_PUBLIC_URL_TEMPLATE` | `https://{slug}.<SITES_BASE_DOMAIN>` |
| `TELEGRAM_BOT_TOKEN` | from @BotFather; enter it in Render only, never in chat or Git |
| `TELEGRAM_WEBHOOK_SECRET` | output of `openssl rand -hex 32` |
| `RESEND_API_KEY`, `EMAIL_FROM` | key with sending access and an address on a verified domain; may stay empty |
| `BUILDER_AI_OPENAI_API_KEY`, `BUILDER_AI_OPENAI_MODEL` | stage AI agent; may stay empty (forms and template drafts still work) |

`SITES_IP_HASH_SALT` and `CODE_HOSTING_TOKEN_ENCRYPTION_KEY` are generated by Render.

## After the first deploy

1. Telegram webhook (once):
   `https://api.telegram.org/bot<TOKEN>/setWebhook?url=<PUBLIC_API_URL>/api/v1/telegram/webhook&secret_token=<TELEGRAM_WEBHOOK_SECRET>`
2. In @BotFather set the Mini App / menu button URL to `PUBLIC_APP_URL`.
3. Staff account: in the `buildpath-api` Shell run
   `STAFF_INITIAL_EMAIL=… STAFF_INITIAL_PASSWORD=… npm run staff:create`.
4. Published sites: add a wildcard custom domain `*.<SITES_BASE_DOMAIN>` to `buildpath-sites` and the DNS records Render shows.
   Owners' own domains for sites are not offered here (`SITES_CNAME_TARGET` stays empty).

## Why the app forwards /api

In production Caddy serves the app and `/api/*` on one address, so the session cookie is first-party. On Render each
service has its own address, so the app (and the admin console) forward `/api/*` to the API themselves over Render's
private network when `API_INTERNAL_URL` is set. The forwarded request carries only the client address that Render's edge
added, and the API trusts exactly one proxy hop (`TRUST_PROXY=true`).
